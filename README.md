# devcontainers

Reusable dev container building blocks — Docker images, copy-and-paste snippets,
and the glue to publish them. This repo is structured so that **adding a new image
is just adding a directory**; the CI pipeline discovers, builds, and publishes it
without any workflow edits. Images may build **on each other** (see Dependencies).

## Layout

```
images/<name>/Dockerfile    one self-contained image per directory
images/<name>/from           (optional) the in-repo parent image's name — one line
images/<name>/README.md      (optional) what the image is and how to use it
ci/select-images.sh          change detection → which targets to build
ci/gen-bake.sh               generates the Docker Bake definition for all images
.github/workflows/build-images.yml   build + publish pipeline
```

Each image directory is its own Docker build **context**, so anything an image
needs (scripts, rootfs overlays) lives beside its `Dockerfile`.

| Image | Published as | Purpose |
|-------|--------------|---------|
| [`base`](images/base) | `ghcr.io/<owner>/devcontainers/base` | Foundation image (no sudo, VS Code channel scrub, unprivileged user); other images build `FROM` it |
| [`default`](images/default) | `ghcr.io/<owner>/devcontainers/default` | `base` + common tooling (gnupg2, yq); the image most projects use |

| [`credential-shelf-aws`](images/credential-shelf-aws) | `ghcr.io/<owner>/devcontainers/credential-shelf-aws` | Vends scoped ≤1h AWS role creds to `/creds/aws/credentials` |
| [`credential-shelf-github`](images/credential-shelf-github) | `ghcr.io/<owner>/devcontainers/credential-shelf-github` | Vends per-org GitHub App tokens (KMS-signed) to `/creds/github/<org>` |

## Adding an image

1. Copy `images/base` to `images/<your-name>/`.
2. Edit the `Dockerfile` (and `README.md`).
3. Open a PR. CI builds it (no publish on PRs); merging to `main` publishes it.

No changes to the workflow are needed — `images/*/Dockerfile` is found
automatically.

## Dependencies (building one image FROM another)

To base a new image on another image **in this repo**:

1. In the `Dockerfile`, write `FROM <parent>` (e.g. `FROM base`).
2. Add a `from` file next to it containing the parent's name (e.g. `base`).

That's the whole contract. `from` drives two things:

- **Build linking** — `ci/gen-bake.sh` turns it into a bake *named context*
  (`contexts = { base = "target:base" }`), so `FROM base` resolves to the base
  **built in the same run**, never a registry pull. Dependent images therefore
  build correctly on PRs and forks, *before* `base` is ever published.
- **Change propagation** — `ci/select-images.sh` rebuilds an image whenever any
  ancestor it depends on changes, not only when its own directory changes.

Dependencies can chain (`a` → `b` → `c`); both the linking and the propagation
are transitive.

## How publishing works

The [`build-images`](.github/workflows/build-images.yml) workflow runs on pushes
to `main`, version tags, pull requests, manual dispatch, and a **weekly schedule**
(Mondays 06:00 UTC) that rebuilds every image to pull in upstream base-image and
OS-package updates:

- **`discover`** runs [`ci/select-images.sh`](ci/select-images.sh), which diffs
  the change and emits the affected images (changed dirs **+ their dependents**)
  as a JSON list. A change to the workflow or `ci/`, a tag push, the weekly run,
  or a manual "build all" rebuilds everything.
- **`build`** runs [`ci/gen-bake.sh`](ci/gen-bake.sh) to produce a Docker Bake
  definition, then builds the selected targets in dependency order with a single
  `docker buildx bake` (per-image GHA layer cache, pushed to **GHCR**). Pull
  requests build but **do not** push.

Tags (generated by `ci/gen-bake.sh`):

| Trigger | Tags applied |
|---------|--------------|
| push to `main` | `latest`, `main`, `sha-<short>` |
| version tag `vX.Y.Z` | `X.Y.Z`, `X.Y`, `sha-<short>` |
| pull request | `pr-<n>`, `sha-<short>` *(built, not pushed)* |

> **Notes**
> - Version tags (`vX.Y.Z`) are repo-wide: pushing one (re)publishes **every**
>   image at that version. Per-image versioning isn't supported yet — `latest` and
>   the immutable `sha-<short>` tag are the stable references for now.
> - Building a dependent also (re)builds and pushes its ancestors, since bake
>   builds the whole dependency chain. Re-pushing an unchanged ancestor is a
>   digest-identical no-op.

## Local build

Builds use bake so intra-repo dependencies resolve (a plain
`docker build images/default` would fail on `FROM base`):

```sh
./ci/gen-bake.sh > docker-bake.json        # generate the definition
docker buildx bake -f docker-bake.json default   # builds base, then default
docker buildx bake -f docker-bake.json --print   # inspect the resolved graph
```

## Running the selector locally

```sh
BASE_SHA=origin/main HEAD_SHA=HEAD ./ci/select-images.sh   # prints images=[...]
BUILD_ALL=true ./ci/select-images.sh                       # force the full set
```
